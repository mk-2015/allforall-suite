## 2. Required matching architecture

Implement a common internal matching interface with separate backends. Select the appropriate backend based on the user's requested matching mode.

### Fixed-string matching: `-F`

Use a dedicated literal-search implementation rather than compiling the input as a regular expression.

- Correctly handle arbitrary literal patterns, including regex metacharacters.
- Support case-insensitive matching when requested.
- Support multiple patterns if the CLI design allows them.
- Optimize large-buffer searches where practical.
- Use SIMD acceleration only when supported and beneficial, with a correct portable fallback.
- Never require AVX-512 to run the program.
- Do not assume that SIMD is always faster; benchmark before claiming performance improvements.

### Standard regex matching: `-G` and `-E`

Evaluate **RE/flex** and **RE2** for their suitability, supported syntax, platform compatibility, and performance.

- Use RE2 as the default safe regex backend if its syntax and semantics meet the selected compatibility contract.
- Consider RE/flex where its C++ API, scanning capabilities, or SIMD support provide a concrete advantage.
- Do not blindly chain the engines or compile every pattern in all engines.
- Define explicit, documented backend-selection rules.
- Preserve predictable behavior and report unsupported regex syntax clearly.

The project's desired behavior is grep-like. GNU grep's default basic regular expressions and `-E` extended regular expressions have different semantics. Do not silently claim full GNU grep compatibility if the selected backend does not provide it. Document any differences and test them.

### Perl-compatible regex matching: `-P`

Use **PCRE2** for genuine Perl-compatible regex support.

- Do not implement `-P` by simply switching to POSIX extended regex.
- Compile patterns once and reuse the compiled pattern during scanning.
- Handle compilation and execution errors cleanly.
- Use the appropriate PCRE2 API and library variant.
- Make Unicode and UTF behavior explicit rather than assuming every byte sequence is valid UTF text.
- Keep optional JIT acceleration optional and provide a fallback when unavailable.

### Common interface

Design an interface that separates pattern compilation from matching. For example, conceptually:

- Compile a pattern and return an error on failure.
- Match a line or buffer.
- Return match spans when highlighting or `-o` requires them.
- Support case sensitivity and the selected matching mode.
- Expose capabilities where backends differ.
- Manage backend resources with RAII.

The example is a design direction, not a demand to use a particular class hierarchy. Choose an implementation that fits the existing repository.

## 3. Grep-style command-line behavior

Inspect the current implementation and preserve useful existing options. Implement or correct the following options where they are already part of the CLI specification:

- `-i`: case-insensitive matching.
- `-v`: select non-matching lines.
- `-w`: match whole words.
- `-x`: match whole lines.
- `-G`: basic regular expressions.
- `-E`: extended regular expressions.
- `-F`: fixed strings.
- `-P`: PCRE2 patterns.
- `-n`: print line numbers.
- `-H` / `-h`: control filename prefixes.
- `-o`: print only the matching portions.
- `-c`: count selected lines.
- `-l` / `-L`: print files with or without selected matches.
- `-q`: quiet mode.
- `-s`: suppress appropriate error messages.
- `-m`: maximum selected lines per input file.
- `-A`, `-B`, `-C`: after-, before-, and surrounding-context lines.
- `-r` / `-R`: recursive directory search, with clearly defined symlink behavior.
- `--include`, `--exclude`, `--exclude-dir`.
- `--color`.
- `--byte-offset`.
- Any other options already implemented and documented in the project.

Do not silently accept unknown options as filenames. Invalid options and invalid numeric arguments should produce useful diagnostics and the appropriate exit status.

Where GNU grep compatibility is intended, verify behavior against it rather than relying on memory.

## 4. Output and matching details

Correctness matters more than the name "Nanosecond Grep."

- Highlight actual matched spans in red when color is enabled.
- Automatically enable color only when appropriate for the output destination, respecting `NO_COLOR` and explicit user overrides.
- Ensure `-o` prints correct match spans and handles repeated or adjacent matches according to the documented semantics.
- Do not copy the entire remaining line for every successive match unnecessarily.
- Implement binary-file handling deliberately. Do not pass arbitrary binary data to a NUL-terminated regex API and pretend it matched the entire buffer.
- If binary bytes are displayed, support the specified `<0xBYTE>` representation and blue coloring when enabled.
- Implement escape-sequence normalization only if it has a clear, documented purpose. If enabled, apply it consistently and use the specified purple coloring for normalized escape sequences.
- Keep matching, decoding, normalization, and rendering as distinct operations so display transformations do not accidentally change search semantics.
- Make `-w` behavior portable and documented; do not rely on non-portable POSIX regex extensions.
- Compute byte offsets correctly, including files whose final line has no newline and files using CRLF line endings.
- Handle empty patterns, empty lines, very long lines, overlapping match candidates, and patterns containing special characters.
- Ensure context lines are neither omitted nor printed repeatedly when multiple matches are close together.

## 5. File and directory processing

- Support standard input where appropriate.
- Handle unreadable files, nonexistent paths, directories, and file read failures cleanly.
- Preserve the distinction between no matches and an operational error.
- Use RAII and avoid resource leaks.
- Avoid following symlink loops during recursive traversal.
- Do not silently swallow every filesystem exception.
- Avoid loading entire large files into memory unless a particular feature requires it.
- Make the implementation portable across supported Linux and BSD environments and Windows toolchains supported by this repository.

Be careful with text-versus-binary semantics and with the limitations of line-oriented APIs such as `std::getline`.

## 6. Portability and performance

AllForAll targets Linux and BSD natively and supports Windows through the project's existing MSYS/Cygwin approach. **Apple/macOS is explicitly excluded.** Follow the repository's actual platform conventions.

- Keep compiler-specific SIMD code isolated.
- Detect CPU capabilities correctly before executing specialized instructions.
- Provide a scalar or otherwise portable fallback.
- Do not use AVX-512, AVX2, SSE, NEON, or other instruction sets without appropriate compile-time and runtime safeguards.
- Avoid assuming x86-specific intrinsics are available on ARM.
- Keep dependency requirements and optional features clear in the build configuration.
- Do not introduce a large dependency merely for a trivial feature without explaining the trade-off.

Prioritize algorithmic efficiency, buffered input, reduced allocations, and compiled-pattern reuse before micro-optimizations.
